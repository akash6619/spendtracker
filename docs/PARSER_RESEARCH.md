# Parser accuracy: research and experiment roadmap

Research date: 2026-09-08. Status: roadmap documented; first deterministic pilot complete.

This is the working plan for evaluating better financial-SMS parsing, merchant
identification, and categorization one approach at a time. The budget target is
₹0 recurring API/hosting cost, using an existing computer and Android phone.
Engineering time, storage, memory, and battery use still count as costs.

The initial recommendation is better contextual rules, then measured experiments
with small models. Google Gemini Nano is an optional device experiment worth
trying early if a compatible phone is available. No model has been benchmarked
against this project's corpus, and no accuracy improvement is claimed yet.

## Scope and existing decisions

This document records research, not adoption of a new production architecture.
D-003 through D-007 in [DECISIONS.md](DECISIONS.md) remain in force: ephemeral SMS,
offline operation, original currencies, current spend policy, and deterministic
rules for the MVP. Model adoption must record an explicit decision and a focused
implementation slice in [MVP_PLAN.md](MVP_PLAN.md). Research can proceed with
synthetic fixtures without changing those decisions.

- No raw SMS storage, logs, inbox exports, or real messages sent to hosted tools.
- Fixtures must be synthetic or irreversibly anonymized, including names,
  identifiers, dates, amounts, and payment handles; masking an account is not enough.
- No new `INTERNET` permission, backend, or paid service as part of these experiments.
- Preserve exact minor-unit arithmetic, INR-only totals, existing inclusion policy,
  idempotency, and protection of user-edited rows under D-019.
- Review reasons exist in data, but review UI is currently hidden under D-018.
  An experiment must not assume a complete correction/review screen already exists.

See [DATA_AND_PRIVACY.md](DATA_AND_PRIVACY.md) and [TESTING.md](TESTING.md).
Some older schema/override descriptions in the documentation predate D-019;
use the current code and later decisions for existing behavior.

## What accuracy means

| Field or decision | Required interpretation | Priority |
| --- | --- | --- |
| Event validity/status | Completed financial event versus OTP, pending, failed, reminder, promotion, or balance-only message | Critical |
| Amount | Amount moved, separated from balance, credit limit, bill due, and other amounts | Critical |
| Currency | Explicit supported original currency and exact minor units | Critical |
| Direction | Debit or credit relative to the user's account | Critical |
| Kind | Purchase, fee, transfer, refund/reversal, withdrawal, or unknown | Critical |
| Spend inclusion | Derived from validated facts and existing policy, with user choice preserved | Critical |
| Time | Source received time today; transaction time is a future policy/schema question | Important |
| Merchant/payee extraction | Actual counterparty span, separated from issuer and payment processor | Important |
| Merchant normalization | Known aliases mapped conservatively to a canonical merchant | Important |
| Category | One of the thirteen current categories, allowing Other/uncertainty | Important |
| Account hint | Optional safe masked last digits | Supporting |
| Payment channel/issuer | Useful extraction context; new durable fields are not assumed | Supporting |
| Source identity | Provider row ID and keyed fingerprint generated by platform code | Critical for deduplication |
| Confidence/reasons | Evidence for uncertainty; measure per field instead of treating a score as proof | Supporting |

Amounts such as balances can be interpreted ephemerally without being persisted.
Source-message deduplication is different from linking multiple messages about
one economic event. Authorization/settlement and bank/provider pairs need a
separate design; never merge solely because amount and time look similar.

Extraction, normalization, and category prediction are separate tasks. An SMS
may identify a payee without revealing what was purchased. Personal transfers,
unknown shops, and mixed marketplace baskets can be intrinsically ambiguous.
Models must be allowed to abstain; a plausible category is not a known fact.

## Current implementation: opportunities to measure

Code reviewed:

- [FinancialMessageParser.kt](../shared/src/commonMain/kotlin/com/spendtracker/core/parser/FinancialMessageParser.kt)
- [TransactionCategorizer.kt](../shared/src/commonMain/kotlin/com/spendtracker/core/categorization/TransactionCategorizer.kt)
- [Transaction.kt](../shared/src/commonMain/kotlin/com/spendtracker/core/model/Transaction.kt)
- [FinancialMessageParserTest.kt](../shared/src/commonTest/kotlin/com/spendtracker/core/parser/FinancialMessageParserTest.kt)

The parser selects the first monetary value and flags differing values as
conflicting. For example, the synthetic text “₹500 debited. Available balance
₹12,000” creates avoidable ambiguity. Direction, kind, and rejection keywords
apply across the whole message rather than the relevant event clause. Merchant
extraction uses a broad expression; sender is available but not used for template
routing. Categorization sees only normalized merchant text. Confidence values
are fixed heuristic scores, not calibrated probabilities.

These are code-review findings, not measured frequency or severity estimates.

## Approach comparison

| Approach | Training location | Inference location | Backend needed? | Cost/fit |
| --- | --- | --- | --- | --- |
| 1. Contextual rules/templates | No training | Shared Kotlin on phone | No | No model overhead; maintenance effort grows with coverage |
| 2. Existing open ML models | Already trained; optional adaptation on computer | Computer first, Android if compatible | No | No inference bill; licence, conversion, size, and domain mismatch need checking |
| 3. Custom small ML | Existing computer; GPU not inherently required | Bundled model on phone | No | Strong budget candidate; labelled data is the main investment |
| 4a. Self-managed local LLM | Pretrained weights; no fine-tuning initially | Computer first, optional Android runtime | No | No API bill; substantial RAM, storage, latency, and integration cost |
| 4b. Hosted LLM | Provider-managed | Provider server | Remote service required, but not necessarily our own server | Network/privacy change and possible API fees; deferred |
| 5. Google Gemini Nano | Google-managed | Android AICore through ML Kit Prompt API | No | Shared system model; device restrictions and quotas apply |

Approaches 2 and 3 need not use LLMs. For a custom classifier, train on a computer,
export a frozen model, and distribute it with the app. The phone has no dependency
on the training computer afterward. Model updates can arrive with app updates.

### 1. Broader, structured rules

Use issuer/template-specific extraction with a conservative generic fallback.
Route using sender plus message structure; sender alone is not proof of a valid
transaction. Resolve the completed event and amount roles before extracting kind,
direction, and merchant. Keep exact money conversion deterministic.

Prioritize personally relevant banks/cards/UPI formats. Each rule gets positive,
nearby-negative, and malformed examples. Expand alias dictionaries and evaluate
explicit user-approved merchant category rules as a separate low-cost baseline.
Avoid growing one global regex or indiscriminately removing merchant suffixes.

### 2. Existing open ML models

Candidate experiments, not endorsements:

- **GLiNER small v2.1:** custom-label entity extraction for merchant, issuer, and
  processor spans. Its card lists English, 166M parameters, and Apache-2.0.
  It is a general extractor, not a validated Indian-SMS model. [S1]
- **Global Financial Transaction Classifier (Mitul Shah):** DistilBERT category
  baseline. The card lists India coverage, MIT licensing, 267 MB, and ten
  categories. Downloads are gated. Its categories do not map cleanly to ours
  (for example, groceries and dining are combined); published scores are
  self-reported and not our benchmark. [S2]
- **Embeddings plus labelled examples:** retrieve similar merchant descriptions
  as an exploratory category baseline. Select a specific model and verify its
  licence before running; similarity does not establish purchase intent.

Start on the computer. Check exact checkpoint licence, dataset provenance, input
format, label mapping, tokenizer, and download access before investing in Android.
ONNX Runtime supports mobile deployment, but conversion/operator compatibility
and actual device performance must be tested. [S3]

### 3. Custom ML trained on labelled data

Start with character/word TF-IDF plus logistic regression, then compare fastText.
These are established lightweight text-classification approaches; fastText also
offers model compression. [S4, S5] Use merchant text and minimal sanitized context
for the thirteen project categories. Exclude irrelevant identifiers from features.

Training on the existing computer can avoid GPU rental. Mobile inference may use
exported linear weights with equivalent tokenization or a compatible runtime;
verify desktop/device prediction parity. Do not assume exporting a model also
exports its preprocessing correctly.

Category labels are cheaper to collect than merchant span labels. If rules still
miss merchant boundaries, evaluate a separate token-labelling model later.
Do not introduce automatic training from private SMS or user corrections: that
requires a separately designed consent/data lifecycle. Existing explicit merchant
rules are useful personalization without model training.

### 4. LLMs: development aid, local runtime, or hosted service

Use an LLM to propose synthetic fixtures, adversarial cases, and draft labels;
human review supplies ground truth. Keep generated variants of the same template
out of both training and test partitions to avoid overstating generalization.

For a local benchmark, select a small instruction model whose licence and runtime
fit existing hardware. Compare structured extraction against the same dataset.
On Android, Google currently directs new work toward LiteRT-LM rather than the
maintenance-only MediaPipe LLM Inference API. [S6] We manage weights, distribution,
memory, and lifecycle ourselves with this route. To preserve no internet
permission, evaluate bundling or manual import rather than an in-app download.

Validate generated fields against source evidence, exact amount parsing, allowed
enums, and policy. Treat SMS as untrusted data, including instruction-like text.
Structured output guarantees neither factual correctness nor a useful confidence
score. Missing evidence must remain unknown.

Hosted LLMs are documented for completeness but deferred. A free tier is not a
durable budget guarantee, and sending SMS off-device conflicts with current scope.
No API account, paid resource, or hosted-message experiment is part of this plan.

### 5. Google on-device AI: Gemini Nano through ML Kit

The **ML Kit Prompt API** supports custom prompts, entity extraction,
classification, and structured output. It is currently beta. [S7] This is a
candidate for optional merchant/category assistance, not an assumed replacement
for the import parser.

Google documents local input/output processing, no per-call server cost, and a
shared AICore model. Prompt support is restricted to listed devices; examples
include OnePlus 13/13s and Pixel 9/10 families. Inference requires the top visible
foreground app. A foreground service does not qualify. Per-app short-term and
battery quotas can interrupt bulk processing. Model versions can differ by
device, so outputs may differ. Recheck the current list before experimenting. [S8]

Check `AVAILABLE`, `DOWNLOADABLE`, `DOWNLOADING`, and `UNAVAILABLE` at runtime.
Initial model/configuration availability may need system downloads; offline
inference is not a guarantee of offline first-time setup. [S9] Verify merged
manifest permissions and SDK/service data handling before adopting the dependency;
local inference alone does not prove our complete privacy contract.

Use a compatible physical phone and synthetic inputs first. Record exact phone,
Android, AICore, SDK, and Nano versions. Measure throttling, app-backgrounding,
model-unavailable behavior, and cold/warm latency. Keep rules available for
unsupported devices and quota exhaustion. Do not queue raw SMS for later AI work.

## Common evaluation protocol

1. Start with a proposed 300–500 safe examples, expanded where coverage is weak.
   This is a practical starting budget, not a sample-size or accuracy guarantee.
2. Label event validity, exact amount/currency, direction, kind, inclusion,
   merchant span/canonical name, category, and legitimately unanswerable fields.
3. Include balance/limit amounts, dual debit/credit clauses, refunds following
   failures, warning footers, malformed amounts, foreign currencies, ambiguous
   payees, and realistic non-financial messages. Use multiple template families.
4. Freeze train/development/test partitions before tuning. Group related template
   variants together. Report separate unseen-template and unseen-merchant tests.
   Fit vocabularies/normalizers on training data only where learned from data.
5. Compare each candidate with both original rules and the latest retained
   baseline. Compare model-only capability separately from the complete hybrid.
6. Report counts/denominators and per-category support; small synthetic results
   do not establish real-inbox accuracy. Do not tune against the held-out test set.

| Metric | What to record |
| --- | --- |
| Detection | Completed-event precision/recall; false accepted and missed events |
| Monetary correctness | Exact amount+currency match; wrong inclusion/exclusion counts |
| Financial impact | Absolute per-event INR contribution error as well as net total error, so cancelling mistakes cannot hide |
| Merchant | Exact span and canonical-name accuracy, including missing/unknown cases |
| Category | Macro-F1, per-category precision/recall, confusion matrix |
| Abstention | Coverage and accuracy among automatic decisions; unresolved-case rate |
| End-to-end | Correct complete records and aggregate totals under unchanged policy |
| Device cost | Cold/warm median and p95 latency, batch time, peak RAM, installed size, battery/thermal observations |
| Reliability | Repeatability, malformed output, quota/error rate, offline/unavailable fallback |

Choose numerical promotion targets before evaluating each candidate, using the
baseline and intended device budget. All critical regression fixtures must pass;
no known privacy, duplicate, user-edit, or exact-money regression is acceptable.
Category gains must not silently change inclusion. Reject or narrow an approach
if gains are marginal relative to its maintenance and device cost.

Gemini Nano is placed early as a potentially inexpensive feasibility check, not
because its accuracy is established. A lack of compatible hardware should be
recorded as a deferral, then the next experiment can proceed without a purchase.

Before starting, claim the experiment ID and unique task identifier in
[STATUS.md](STATUS.md), mark it In progress here, and avoid overlapping active
work. For production edits, first promote a focused slice to MVP_PLAN with
acceptance criteria. At handoff, record results here and clear the active row.

Research-only comparisons need reproducible evaluation and fixture/privacy checks.
Production changes must pass [TESTING.md](TESTING.md), including shared/Android
unit tests, lint, debug assembly, and connected tests for affected Android/UI
boundaries. Model device claims require physical-device measurements.

## Experiment results log

### PAR-01A — Amount roles and merchant boundaries

- Date/owner/status: 2026-09-09, `/root`, retained and complete.
- Hypothesis: explicitly labelled balance/limit values and instrument-like
  merchant candidates account for high-impact, safely correctable rule failures.
- Dataset: 30 synthetic payment cases with original/lowercase/whitespace
  variants (90 evaluations), plus 12 rejected and 6 ambiguous cases with the
  same variants (54 safety evaluations). This is a focused regression pilot,
  not a representative or held-out real-inbox dataset.
- Original parser result: 72/90 exact amount+currency, 66/90 merchant, 36/90
  inclusion, 33/90 without amount conflict, and 15/90 complete. Because each
  source case has three formatting variants, complete coverage was 5/30 base cases.
- Updated parser result: 90/90 for every payment field above and 54/54 safety
  cases. Additional property-style combinations confirm that four balance/limit
  labels before and after eight event types preserve all other parsed facts.
- Change: adjacent explicit balance/credit-limit amounts are removed from
  transaction candidates, unless a completed-event verb immediately follows the
  amount. If only contextual amounts remain, the event has no transaction amount.
  Other differing amounts remain conflicting and excluded. Merchant extraction
  skips card/account descriptions and recognizes more metadata boundaries.
- Version/reliability: parser output advanced from 3 to 4. Untouched rows can
  refresh on re-import; user-edited rows remain frozen under D-019. No schema,
  UI, SMS-provider, permission, network, or background-work change.
- Validation: shared JVM tests, Android unit tests, Android lint/debug assembly,
  and iOS simulator shared compilation passed. Connected tests were not required
  for this shared-only slice.
- Limitation/next step: the result establishes regressions for the chosen cases,
  not broad accuracy. PAR-00 remains ready to build a frozen multi-bank baseline;
  issuer routing and broader direction/status rules should be driven by it.

## Open questions

- Which physical phone and Android version can be used for Nano? Compatibility
  has not been established; owning a phone with Gemini features is not enough.
- Which banks, template families, and languages should PAR-00 prioritize?
- What accuracy/coverage and latency/size targets are justified by the baseline?
- How should an adopted model's suggestions be confirmed or represented in UI?
- Is transaction-time extraction or economic-event reconciliation worth a
  separate slice? Neither stored-time policy nor deduplication policy changes here.
